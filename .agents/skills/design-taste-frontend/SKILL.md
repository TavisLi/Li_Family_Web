# Design Taste Frontend

## Scope and precedence

Use only for the specific deliverable named in this skill, within the approved scope. Current user scope and repository canonical decisions override every technique, package, font, icon, image-count and output default below. Existing-pattern fixes do not trigger redesign or image generation. Read the repository operating contract for authority; this skill grants no external-write, Production, destructive or merge authority. Reuse valid approvals; ask only for consequential missing choices.

## Select only the relevant technique sections

The original technique capability is preserved in [design-techniques.md](references/design-techniques.md). It is a task-scoped reference, not startup context. Search the named headings and read only applicable sections:

- Requested redesign: sections 0 (brief inference) and 11 (redesign protocol).
- New landing/portfolio visual direction: sections 2 and 4; section 1 only to calibrate its dials.
- Stack integration: section 3, subject to the repository's installed packages and architecture.
- Motion: sections 5 and 6 only when the requested design needs motion.
- Block-library work: section 12 only for an actual block-library deliverable.
- A specifically selected design system: its applicable Appendix A/B/C material; never all appendices by default.
- Final design review: relevant checks in sections 9/14; do not expand a routine change into a full-page redesign.

Declare a design direction only when doing design; infer routine details from existing repository evidence. Keep existing packages, fonts and icons. Proposing an install is not approval or an instruction to switch stack. Run task-required validation rather than every visual ritual. Preserve user assets and functionality.
