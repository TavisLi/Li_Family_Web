## 1. 文件定位與優先級

- `CONTEXT.md`：穩定領域詞彙。
- `docs/adr/`：已接受的持久架構決策。

## 2. 產品願景

Web Li 是一個長期營運的家庭數位入口，目標是：

1. 保存數十年的家庭身份、文字、照片、旅行與共同願望。
2. 讓內容可由 Payload Admin 日常維護。
3. 讓版本化 source material 可以安全重複匯入。
4. 對公開訪客與家庭成員提供不同但一致的產品體驗。
5. 在程式、資料與媒體層都具備可回溯、可驗證、可復原的營運方式。

高級視覺不是特效數量，而是清楚資訊層級、克制動態、內容優先、可靠 fallback、響應式排版與無障礙行為。任何動畫與裝飾都不得犧牲閱讀、效能或存取邊界。

## 4. 核心架構原則

### 4.1 Next.js 與 Payload

- 使用 Next.js App Router，不使用 `pages/`。
- Payload v3 嵌入 Next.js，透過 `withPayload`。
- Admin route 固定為 `src/app/(payload)/admin/[[...segments]]/page.tsx`。
- Route／feature component 不直接呼叫 Payload Local API。
- 所有 runtime data access 由 `src/lib/data/` 封裝。

### 4.2 目錄責任

```text
src/app/          Next.js routes、layouts、loading、error、metadata
src/features/     Domain UI、actions、feature-level tests
src/components/   通用無狀態 UI
src/lib/data/     Payload data access 與 access-aware queries
src/lib/          Domain projection、media、utility
src/payload/      Collections、Globals、Payload config、generated types
src/scripts/      Seed、audit、read-back、controlled operations
src/migrations/   Payload migrations
content-source/   Versioned Markdown、assets、manifest input
docs/             Architecture、catalog、operations、Phase evidence
public/           公開靜態資產
```

所有應用源碼位於 `src/`；只有 route code 必須位於 `src/app/`。

### 4.3 型別

- Payload Collection 是 database schema 的實作 source of truth。
- Collection 變更後執行 `pnpm exec payload generate:types`。
- 前端與 domain projection 從 `src/payload/payload-types.ts` 派生。
- 不用 `any` 或手寫重複 schema 逃避 generated types。
- UI-only type 可以存在，但不得冒充持久化 schema。

### 4.4 效能與資料庫

- 使用 Supabase pooler，避免每個資料讀取建立獨立無界連線。
- 是否並行讀取必須依 query 數量、pool capacity、failure isolation 與 route latency 決定；不強制所有首頁 query 使用 `Promise.all()`。
- 大量資料採分頁／限制欄位／適當 depth，不一次讀取完整歷史。
- Dynamic import 只用於真的需要 client-only 或大型 bundle 的功能。
- 效能門檻以實測為準，不用無證據的固定分數宣稱完成。

## 5. 內容 Ownership

### 5.1 三個責任層

1. **Catalog／content-source**：版本化輸入與 stable identity。
2. **Payload published records**：Production runtime source of truth。
3. **GitHub／Vercel**：程式與部署版本。

修改 catalog 或 Markdown 不會自動修改 Production。

### 5.2 Base／Source／Current

當內容同時允許 Source import 與 Admin editing：

- Base：上次接受的 source projection。
- Source：本次 parser 結果。
- Current：Payload 現況。

Safe reconciliation：

- Source-only change → update。
- Current-only change → preserve。
- 雙方不同修改 → conflict。
- Missing Base legacy record → preserve-current。

任何 `source-wins` 必須先有 conflict report 與 Production write 批准。Payload-to-source export 只產生 draft artifact，不直接覆蓋 parser input。

### 5.3 Media

- 圖片實體檔存於 Cloudflare R2，由 Payload Media record 管理 metadata 與 relationships。
- 不引入 Vercel Blob。
- 影片只保存合法 YouTube URL／metadata，不上傳 `.mp4`、`.mov`。
- Media sync 採差異比較；禁止為單一缺圖全量重傳。
- 缺圖使用 `ImageFallback`，但發布完成仍需驗證真實媒體。

## 6. 存取與隱私

### 6.1 Public mode

只回傳明確公開的 records。私密內容不得出現在：

- Page body
- Server-rendered HTML
- Metadata
- JSON-LD
- RSC payload
- Public media relationship

### 6.2 Family mode

由有效 Payload user session 建立。Family mode 可解鎖 family-only reads 與被授權互動，但不等於 Payload Admin 或 Production operator。

### 6.3 Admin

Administrator 可依 access control 管理 Payload 內容。Admin 權限不自動包含 migration、seed、環境變數或 destructive cleanup 權限。

### 6.4 Secret

`PAYLOAD_SECRET`、`DATABASE_URI`、R2 credential、cookie、password 不得進入：

- Client component
- Git
- Issue／PR
- Completion Report
- Test fixture
- Console output

## 7. 產品模組

### 7.1 Family Lobby

根路由 `/`：

- 介紹家庭與成員入口。
- 呈現被授權的旅行、文章、時間軸與家庭模組摘要。
- Public／Family mode 內容不同，但視覺結構應穩定。
- 資料聚合必須經 data layer，並避免 pool exhaustion。

### 7.2 Member Profiles

動態路由 `/member/[slug]`：

- 顯示身份、興趣、里程碑、履歷敘事與媒體。
- 人物內容與登入帳號是不同概念。
- 可配置媒體與聯絡資訊由 Payload 管理。

### 7.3 Premium Family Blog

路由 `/blog`、`/blog/[slug]`：

- Payload Posts／Categories。
- Lexical richText。
- Author、category、tag、cover、published date、visibility。
- 公開文章可產生正確 metadata／JSON-LD。
- Comment／reaction write 僅限授權 session。

### 7.4 Family Access Gate

- `/family/login` 建立 family session。
- Private route 與 interaction 在 server/data layer 驗證。
- 未登入可顯示不含私密資料的 locked preview。

### 7.5 Timeline

路由 `/timeline`：

- 依日期呈現家庭事件。
- 可關聯成員、文章、旅行或 bucket item。
- 大量歷史資料需採分頁或受限讀取。

### 7.6 Bucket List

路由 `/bucket-list`：

- Family-only。
- Wish pool、in progress、completed。
- 完成時以可重複安全的 workflow 建立 linked private Timeline Event。

### 7.7 Annual Wrapped

路由 `/wrapped`：

- Family-only 年度故事。
- Payload `wrapped-snapshots` 保存可發布 snapshot。
- 不以 client-side 隱藏取代 access control。

## 8. Travel Domain

### 8.1 領域模型

旅行不是單一 `TravelProject.status`：

- `travel-plans`：未來旅程的規劃與討論。
- `travel-memories`：行後整理與分享作品。
- `travel-route-identities`：跨 collection canonical slug ownership。

Plan 日期已過時成為 lobby 的 Archived Plan，但 persisted record 仍是 Plan。Memory 可以 optional `originPlan` 連回 Plan，必須使用不同 canonical slug。

### 8.2 Planning canonical content

`planningSections` 是 Plan 的 canonical content unit，保存：

- Anchor／排序
- Display labels
- Localized body
- External links
- Media
- Comment／thumb-up／thumb-down settings

Legacy flights、lodgings、daily itinerary 等 projection 不自動等同 planning domain truth。

### 8.3 Runtime

- `/travel` 聚合 Plan、Memory 與 Archived Plan。
- `/travel/[slug]` 透過 route identity 解析 owner。
- Renderer 使用由 generated `TravelPlan`／`TravelMemory` types 派生的 union projection。
- Seed 依 catalog status 導向 Plan 或 Memory，不再日常寫入 legacy `travel-projects`。

### 8.4 Phase 17 過渡狀態

- Additive collections／relationships。
- Production controlled migrations。
- 5-record copy。
- Route identities 與 shadow relationship copy。
- RLS／grants security migration。

- PR #59 merge 與 Production deployment。

仍保留：

它們只作 rollback 與觀察期證據。Issue #50／#57 的 destructive cleanup 需要獨立 inventory、backup、runtime observation、approval 與 read-back。ADR-0008 記錄 2026-07-29 只適用本次 Phase 17 cleanup 的 no-backup waiver；一般 destructive migration 的備份要求不變。

## 10. Migration 與 Production Data

### 10.1 原則

- 不手寫 Prisma／Drizzle schema。
- Collection change → generated types → migration → review → rehearsal → approval → apply → read-back。
- 預設 additive、nullable、backward-compatible。
- 任何 warning 指向 data loss 或 schema drift 時停止。

### 10.2 授權分離

下列動作分別批准：

- Migration
- Baseline metadata
- Content update
- Media upload
- Relationship cutover
- RLS／grants
- Destructive cleanup

### 10.3 Production evidence

Approval package 至少包含：

- Target environment
- Current inventory
- Migration／script hash
- Expected mutation counts
- Stop conditions
- Rollback
- Before／after query
- Read-back result

## 11. Git、Preview 與 Production

- `main` 是 Production branch，不直接 push。
- 從最新 `main` 建立 `codex/phase-*`、`codex/docs-*` 或明確修復分支。
- 所有變更透過 PR。
- PR Preview 必須完成 scope-appropriate QA。
- 合併後確認 Production deployment commit。
- Vercel `READY` 不代表 route、database、metadata 或 access 已驗證。

Production gate：

1. Deployment commit
2. Key route HTTP
3. Rendered HTML
4. Canonical／Open Graph 正式網域
5. Public／Family access
6. Runtime logs
7. R2 asset
8. Data read-back（若適用）
9. Rollback candidate

## 12. Phase 治理

Phase 流程固定使用 `docs/phase-execution-playbook.md`。

完成狀態：

`Implemented → Locally verified → PR ready → Merged → Production verified → Closed`

Completion Report 放在 `docs/phase-completion-reports/`，且不能用：

- Build 代替 runtime。
- Source change 代替 data sync。
- Vercel READY 代替 Production verification。
- 舊 read-back 代替新失敗結果。
- 一般 Phase approval 代替 destructive authority。

## 14. 架構完成標準

一項架構變更只有在以下條件成立時才算完成：

- Domain wording 與 `CONTEXT.md` 一致。
- 未衝突或已 supersede 相關 ADR。
- Collection、generated types、migration 一致。
- Data layer 與 renderer 使用新模型。
- Public／Family access 測試通過。
- Preview／Production evidence 符合 Phase scope。
- 舊路徑是否保留、何時清理與 rollback 已明確記錄。
