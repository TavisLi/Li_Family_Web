## 1\. 專案願景與世界級審美標準

Web Li 是一個定位為長期運營、承載數十年家庭記憶與情感的數字聖殿。本專案不以「完成基礎功能」為終點，而是全面對標世界一流（World-Class）網頁設計、產品工藝細節、人機互動、長期可持續性與隱私安全。本文件作為AI代理人（Claude Code / CODEX / Google Antigravity 等）與開發團隊的最高指導原則。

### 1.1 氛圍感知美學 (Ambient UI)

全站拒絕採用死板、突兀的深色/淺色切換。系統必須實作動態色彩過渡美學（Dynamic Thermography），讓網頁物理氛圍隨著當前瀏覽的主角或內容進行「呼吸式」轉變：

-   Tavis Li (爸爸)：當切換至Tavis的頁面或半導體科技板塊時，全站的滾動條、毛玻璃邊框與動態背景將平滑過渡為 Google/Apple 風格的極簡冷調科技藍。
    
-   Lynn Chien (媽媽)：當切換至Lynn的頁面時，全站色調轉入暖調莫蘭迪米黃，營造優雅、溫潤的高雅視覺。
    
-   Leo Li (兒子)：當切換至Leo的頁面時，全站過渡為賽博極客風（深黑底色配上絲滑的螢光綠微弱光暈）。
    

### 1.2 電影級動態與微互動

極致的質感來自於隱顯之間的微小細節。所有動畫效果必須遵循物理規律，拒絕線性過渡。

-   Canvas 粒子動畫：首頁與各歡迎區的粒子動畫不可僅是隨機漂浮，需具備鼠標引力磁場與滾動驅動動畫 (Scroll-driven Animations)。
    
-   文字動畫：文字在滾動時應具備從毛玻璃後方逐漸聚焦放大的電影質感。
    
-   3D Hover 特效：所有卡片元素均需配置 3D Hover 傾斜特效與彈簧物理動畫 (Spring Physics)。

## 2\. 系統技術棧選型 (Tech Stack)

基於長期的效能、托管成本與可維護性評估，全面採用以下現代高擴展架構：

| 核心模組 | 選型技術 | 架構定位 |
| --- | --- | --- |
| 核心網頁框架 | Next.js 15 (App Router, TypeScript) | 全棧渲染、Server Components 效能優化。版本需符合 Payload 官方兼容矩陣，優先採用 Next.js 15.4.x（最低 15.4.11）。 |
| 內容管理系統 | Payload CMS v3 (Embedded inside Next.js) | 單一真理源 (Single Source of Truth) |
| 資料庫系統 | Supabase PostgreSQL (連接池模式) | 動態數據與持久化存儲 |
| 媒體與文件儲存 | Cloudflare R2 (S3 Adapter) + Cloudflare CDN | 海量像片與圖片高畫質存儲及分發。<br><br>影像優化管道：Cloudflare Transform (自動轉換 WebP/AVIF 格式與尺寸壓縮) |
| 多語系支援 | next-intl (預設: zh-TW, 備用: en) | 全站靜態與動態內容國際化 |
| 前端樣式與動畫 | Tailwind CSS / shadcn/ui / Framer Motion | 原子化樣式、Radix 原生無障礙組件與物理動畫 |
| 部署與 CI/CD | GitHub Repository + Vercel Deployment | 自動化流水線, main 分支推送即時部署 |

### 核心架構約束

1.  **零原生影片儲存**：專案嚴禁提供上傳、解碼或串流原生影片檔案（如 .mp4, .mov）的功能。所有影片在資料模型與 UI 層，均需以「YouTube 外部連結網址」的形式存在。多媒體組件遇到影片類型時，需調用 YouTube Thumbnail API 渲染預覽圖，並透過前端燈箱（Lightbox）內嵌 iframe 進行播放。
    
2.  **媒體儲存去 Vercel 化**：所有像片及靜態圖片資產，必須透過 S3 適配器上傳至 Cloudflare R2。嚴禁引入 Vercel Blob。
    
3.  **數據庫冷啓動防護**：數據庫已切換至 Supabase PostgreSQL。編寫後端與 CMS 連接代碼時，必須使用連接池埠（Port 6543）並在連接字串帶上 ?pgbouncer=true，以避免 Serverless 連接暴增與冷啓動延遲。
    
4.  **數據獲取層隔離**：所有數據請求通過src/lib/data/封裝函數，前端禁止直接調用Payload Local API

5.  **圖片字段容錯**: 所有Collection中的圖片/媒體關聯字段必須設置為required: false

## 3\. 核心功能模組需求

### 3.1 全域家庭大廳 (Family Lobby)

作為 Web Li 數字聖殿的第一接觸點，根路由 (/) 必須展現頂級的產品工藝與家庭凝聚力。首頁作為全站的數據中樞與流量入口，需具備以下核心特性：

-   **全景英雄首屏 (Hero Section) 與 Ambient UI 零點**：

    -   預設全站基調為高雅極簡的「中性毛玻璃 (Neutral Glassmorphism)」。
  
    -   搭配全螢幕的 Canvas 粒子動畫。當鼠標懸停或滑動至特定家庭成員的入口卡片時，粒子磁場與全站色調需無縫預加載並過渡至該成員的專屬氛圍（如：指向 Tavis 時轉為科技藍，指向 Lynn 時轉為莫蘭迪黃）。

-   **家族成員矩陣入口 (Family Portal)**：

    -   透過 3D Hover 物理彈簧卡片，展示 6 位家庭成員（Tavis, Lynn, Nini, Leo, Sophie, Grandma）的動態立繪或質感頭像。

    -   卡片需呈現成員的「一句話動態或當前狀態（Status）」，點擊後通過絲滑的頁面過渡動畫進入原定的「個人首頁」。

-   **動態聚合看板 (Dynamic Feed Hub)**：

    -   **近期足跡**：自動提取 TravelProjects 中「規劃中」與最新「已完成」的行程橫幅（Banner），提供快速一鍵參與評論與點贊的入口。

    -   **家庭速報**：聚合最新的 Premium Family Blog 文章輪播，並展示最新的情感互動留言板摘要。
 
    -   **時空膠囊微縮窗（Time Machine Widget）**：首頁動態拉取歷史上「那年今日（On This Day）」或隨機年份的家庭核心大事記快照與一張歷史像片，作爲跳轉至獨立 3.6 模組 的情感引流入口。
      
    -  **共同願望精簡看板（Bucket Items Quick View）**：【家人模式限定】首頁卡片式展示當前「進行中」優先級最高的前 3 項共同願望。支援在首頁直接勾選完成（同步觸發 Canvas 全螢幕煙火特效），並提供「查看完整願望清單」按鈕引導至獨立的 3.7 頁面

-   **門禁感知渲染 (Role-Aware Rendering)**：

    -   落實 3.5 的雙模隱私機制。未登入的訪客僅能看到中性首屏、公開成員入口與公開旅遊/文章區塊。

    -   家人解鎖登入後，首頁無感局部刷新，額外浮現「家庭共同願望清單 (Bucket List)」入口、「年度時光報告預告」以及私密照片瀑布流概覽。

### 3.3 旅遊與規劃互動系統 (Travel Projects)

每一個旅遊項目必須以獨立的一個以上網頁呈現，其底層數據必須嚴格解析travel-projects.md及其關聯的外部旅遊文件。項目區分為「規劃中」與「已完成」兩種狀態。

-   **規劃中行程** (如 202607 重慶)：
    
    -   **數據解析源**：嚴格解析 202607重慶長江三峽8日.md，提取6人出行名單、航班資訊(MU3539, 3U3784)、住宿交通與核心防暑降溫提醒。
        
    -   **高密度互動組件**：頁面的各項細分內容(如飯店選擇、景點排程、費用估算)必須啓用讓用戶添加 comment、Thumb-up 和 Thumb-down 的功能, 人添加評論(comments)、點贊(Thumb-up)與點踩(Thumb-down)的功能，且必須清晰展示操作者的用戶名。且必須清晰展示操作者的用戶名, 以輔助家庭決策。
        
-   **已完成行程** (如 202308 東澳)：
    
    -   **數據解析源**：嚴格解析 202308東澳全覽9日.md，提取其墨爾本古董蒸汽火車、企鵝歸巢、悉尼藍山等核心裡程碑、航班與小費細節。
        
    -   **回憶分享組件**：視覺上轉為莫蘭迪色系暖色調，著重於旅遊心得、大圖瀑布流照片（Masonry Layout）與 YouTube / 雲端平台影片連結的流暢嵌入與點擊播放。
        

### 3.4 頂級家庭部落格系統 (Premium Family Blog)

為滿足家庭長期的思想沈澱、生活隨筆與知識分享需求，全新引入世界級規格的 Blog 模組。

-   **模組化區塊編輯器 (Block Editor)**：後台採用 Payload CMS 的 Rich Text (Lexical) 區塊系統，支援家人無痛嵌入式多種組件 (如：Markdown 語法、精緻的代碼高亮區塊、流暢的大圖排版、YouTube 影片、或是家庭成員專屬的投票與代辦元件)。
    
-   **深度成員關聯**：每篇 Blog 文章需強關聯作者（authors），並在前端展示極具質感的作者 Hover Card（浮動卡片），滑動顯示該成員的最新動態、精簡履歷與快速對話通道。並可透過鏈接跳轉到相對應的個人首頁。
    
-   **多維度分類與動態標籤雲**：支援按照多種維度進行交叉篩選。前端實作具備微弱物理碰撞效果的標籤雲（Tag Cloud）。
    
-   **情感互動留言板**：每篇 Blog 下方除了常規文字評論外，加入專為家人設計的「暖心表情快速回應」（如：溫馨、太酷了、贊、辛苦了），且評論與回應必須支持 useOptimistic 樂觀更新，達成無延遲互動。
    
-   **多語系SEO優化**：自動生成具備正確語系標籤的靜態頁面(ISR)，內建JSON-LD結構化數據。
    

### 3.5 門禁與雙模隱私系統 (Family-Only Secure Gate)

家庭入口網站涉及高度敏感的隱私數據。系統必須具備**公開（Public）與私密（Family-Only）雙模切換機制**。

-   **訪客模式 (Public)**：未登入的外部訪客僅能看見公開的成員介紹、公開 Blog 文章、公開的旅遊合影與精簡大事記。
    
-   **家人模式 (Private)**：家庭成員通過後台驗證或前端安全 Session 暗號解鎖後，系統採用無感局部刷新，解鎖完整的敏感相冊、吐槽點評、詳細日程與個人成長足跡。
    

### 3.6 時間軸大事記 (Timeline event)

打破扁平的大事記流水帳，引入「時空滑塊（Time Machine Slider）」概念。當使用者在時間軸上拖動年份（例如從2026拖回2013）時，網頁主體色調將短暫泛黃，頁面透過動態濾鏡與動畫，自動過渡並聚焦至該年份的家庭核心事件、當時成員的青澀頭像與歷史像片，創造強烈的情感震撼。

-   **架構定位**：本模組為獨立的前端渲染路由頁面 (/timeline)。打破扁平的大事記流水帳，作為承載家庭數十年長週期記憶的沈浸式空間，並與 3.1 首頁 的微縮窗口進行動態聯動。
  
-   **時空滑塊互動**：引入「時空滑塊（Time Machine Slider）」概念。當使用者在時間軸上拖動年份（例如從2026拖回2013）時，網頁主體色調將短暫泛黃，頁面透過動態濾鏡與動畫，自動過渡並聚焦至該年份的家庭核心事件、當時成員的青澀頭像與歷史像片，創造強烈的情感震撼。

-   **效能隔離防線**：本頁面涉及海量歷史文本與像片載入，數據獲取層（lib/data/timeline）必須實作滾動非同步分頁加載（Infinite Scroll）與圖片 R2 尺寸優化，嚴禁一次性拉取全量數據，確保與首頁物理隔離。

### 3.7 年度時光報告與共同願望清單 (Annual Wrapped & Bucket List)

本模組由兩個獨立的私密互動路由空間組成，僅在「家人模式（Private）」下全面解鎖，並在 3.1 首頁 保留高互動性的數據輕量化接口。

-   **家庭共同願望看板 (Family Bucket List - 獨立頁面 /bucket-list)**：
  
    - 全家共同維護的看板系統。分為「願望池」、「進行中」、「已實現」三大狀態。
 
    - 當家人在 3.1 首頁微縮組件 或本頁面中勾選完成時，全站即時觸發 Canvas 螢幕煙火特效，並自動將該事件歸檔至 3.6 時間軸大事記 中。

### 4.1 專案結構要求

專案結構必須保持高度模組化，明確劃分「通用組件」與「業務功能域」，以利多代理（Multi-Agent）並行開發時減少代碼衝突。其他規範如下：

1.  **統一的源碼隔離 (The src Directory)**：所有應用代碼必須放置在 src/ 目錄下。這使得根目錄僅保留環境設定與文檔，極大地降低了 AI 代理人在執行終端操作時的路徑誤判率。
2.  **嚴格邊界**：禁止將帶有業務邏輯的組件直接丟進 src/components/。必須採用 Feature-Driven 架構。你所開發的代碼若屬於特定業務，必須嚴格限縮在 src/features/[member|timeline|travel|home|admin]/ 資料夾內，以確保與其他並行開發的智能體互不干涉。
3.  **數據調用防護**：前端任何 Server/Client 組件均不得直接調用 Payload 的 Local API（如 payload.find）。所有數據請求必須導向 src/lib/data/ 層對應的封裝函式。
4.  **效能與 SEO 要求**：
    -   所有前台 `page.tsx` 必須包含 `generateMetadata` 導出，且必須妥善處理圖片的 Open Graph 預覽 URL。
    -   所有圖片組件必須使用 Next.js `Image` 並配置精確的 `sizes` 屬性。
    -   複雜動畫組件必須使用 next/dynamic 進行非同步載入。

### 4.2 全域原始數據隔離與內容源數據（content source）規範

為了確保全棧架構的純淨度，並為後續自動化數據灌錄（Data Seeding）打下基礎，系統強制執行「程式碼與原始內容完全解耦」原則：

1. **專屬目錄設立與結構定義**：於專案根目錄下設立獨立的 `content-source/` 資料夾（內含 `profiles/` 與 `travels/` 子目錄）。嚴禁將原始 Markdown 內容文件混入 `src/app/` 或 `src/components/` 等程式碼核心目錄。
3. **單一事實來源（SSOT）**：`content-source/` 內的 Markdown 文件為系統初始化的唯一文本依據。
4. **動態擴充性與自動化構建（核心架構要求）**：未來新增旅遊項目或個人檔案時，用戶只需將新的 `.md` 文件放入 `content-source/travels/` 或 `content-source/profiles/`。系統後續開發的自動化腳本（Seeding Scripts）必須具備遍歷該目錄、解析 Markdown 內容並動態新增至 Payload 數據庫條目的能力。
5. **前端路由動態感知（防呆紅線）**：前端頁面必須透過動態路由（Dynamic Routing，如 `[slug]` 或 `[id]`）自動讀取數據庫內容並渲染。**嚴禁在應用程式中手寫硬編碼（Hardcoded）的死路由**。
6. **Token 消耗優化**：在開發前端視圖時，AI 代理人應直接引用 Payload 自動生成的強類型（`payload-types.ts`），嚴禁在前端組件中直接引入或重復掃描解析 `content-source/` 內的大型文本文件。

## 5\. 核心資料模型設計 (Payload Collections)

Payload CMS 的 Collection 配置是本系統資料庫的唯一真理源 (Single Source of Truth)。本章節僅定義業務層面的數據結構與約束，開發代理 (AI Agent) 必須自行查閱最新 Payload v3 官方文件，使用最新的語法（如 import type { CollectionConfig } from 'payload'）來實現具體的 TypeScript 代碼。

### 5.1 Posts (部落格文章模型)

* **定位**：承載家庭的思想沈澱與生活隨筆。
* **權限設定 (Access Control)**：已登入的家庭成員可讀取所有文章；未登入訪客僅能讀取 `isPrivate: false` 的公開文章。

| 字段名稱 (Name) | 數據類型 (Type) | 必填 (Required) | 業務設定與說明 (Description / Settings) |
| --- | --- | --- | --- |
| title | text | 是 | 支援多語系 (localized: true)。在 Admin UI 作為標題顯示。 |
| slug | text | 是 | 唯一值 (unique: true)。 |
| author | relationship | 是 | 關聯至 `users` Collection。 |
| categories | relationship | 否 | 關聯至 `categories` Collection，支援多選 (hasMany: true)。 |
| isPrivate | checkbox | 否 | 預設為 `true`。標示為私密文章（僅限家庭成員）。 |
| publishedDate | date | 是 | 文章發佈日期。 |
| coverImage | relationship | 否 | 關聯至 `media` Collection。（注：Phase 1 設為非必填以容錯） |
| content | richText | 是 | 必須使用 Lexical 區塊編輯器，支援多語系。 |
| tags | array | 否 | 包含子字段 `tag` (text)。 |

### 5.2 TravelProjects (旅遊行程模型)

* **定位**：管理「規劃中」與「已完成」的家族旅遊專案，並與外部 Markdown 檔案建立對應。

| 字段名稱 (Name) | 數據類型 (Type) | 必填 (Required) | 業務設定與說明 (Description / Settings) |
| --- | --- | --- | --- |
| title | text | 是 | 支援多語系。在 Admin UI 作為標題顯示。 |
| status | select | 是 | 選項：`['planning', 'completed']`。 |
| isPrivate | checkbox | 否 | 預設為 `true`。 |
| startDate | date | 是 | 行程開始日期。 |
| endDate | date | 是 | 行程結束日期。 |
| externalDocIdentifier | text | 否 | 對應 `content-source/travels/` 下外部 Markdown 文件的識別碼。 |
| coverImage | relationship → media | 否 | 封面照片、圖片。 |
| members | relationship → users (hasMany) | 否 | 參與成員。 |

### 5.3 Comments (全站情感互動模型)

* **定位**：統一管理全站（文章、旅遊規劃、大事記）的留言與表情互動。

| 字段名稱 (Name) | 數據類型 (Type) | 必填 (Required) | 業務設定與說明 (Description / Settings) |
| --- | --- | --- | --- |
| user | relationship | 是 | 關聯至 `users` Collection。 |
| associatedType | select | 是 | 選項：`['travel', 'timeline', 'blog']`，標明此留言屬於哪個模組。 |
| associatedId | text | 是 | 關聯模組的具體內容 ID（例如某篇文章的 ID 或某個行程的 ID）。 |
| commentText | textarea | 否 | 用戶的文字留言（若僅發送表情則為空）。 |
| reaction | select | 否 | 選項：`['none', 'up', 'down', 'heart', 'cool', 'applause']`。 |
| createdAt | date | 是 | 留言建立的時間戳記。 |

### 5.4 Media (媒體流水線模型)

配合 Cloudflare R2，所有像片上傳流程由 afterChange 鈎子 (Hook) 自動觸發 Sharp 處理。原始高畫質圖留存 R2，前端根據 sizes 欄位異步加載 400px (Thumbnail), 800px (Medium), 1600px (Large) 的 WebP 圖片，嚴格杜絕 LCP 效能瓶頸。

* **開發特別注意**：在 Phase 1 本地開發階段，**請先配置為本地存儲（允許寫入本地資料夾）**，以確保系統可順利啓動與驗證。後續 Phase 才會引入 Cloudflare R2 S3 Adapter，嚴禁在初始階段加入 `disableLocalStorage: true`。

| 字段名稱 (Name) | 數據類型 (Type) | 必填 (Required) | 業務設定與說明 (Description / Settings) |
| --- | --- | --- | --- |
| type | select | 是 | 選項：`['photo', 'video']`。預設為 `photo`。 |
| youtubeUrl | text | 否 | 僅當 `type` 為 `video` 時顯示於後台。需加入 Regex 驗證確保為合法 YouTube 網址。 |
| altText | text | 是 | 支援多語系。用於無障礙說明與 SEO。 |
| tags | array | 否 | 包含子字段 `tag` (text)。 |
| relatedMembers | relationship | 否 | 關聯至特定的家庭成員 (hasMany: true)。 |
| relatedTravel | relationship | 否 | 關聯至特定的旅遊行程 (hasMany: false)。 |

* **圖片處理要求**：後台需配置 `imageSizes`，自動裁切並產生 `thumbnail` (400px), `medium` (800px), `large` (1600px) 三種尺寸。

### 5.5 SiteConfig (全站設定 - Global)

* **定位**：為了保持單一真理源，全站唯一的設定資訊必須配置在 Payload 的 `Globals` 中，而非 `Collections`。

**A. SiteConfig (系統底層設定)**

* 字段包含：`siteName` (多語系文字), `siteDescription` (多語系文本區), `contactPhone`, `contactEmail`, `contactAddress` (多語系)。
* 陣列字段：`socialLinks`，包含 `platform` (下拉選單如 github, linkedin) 與 `url`。

**B. HomeConfig (首頁動態配置)**

* 權限設定：必須設定為公開可讀 (`read: () => true`)。
* 字段包含：`heroTitle` (預設 'Welcome to Web Li'), `heroSubtitle`, `heroBackground` (關聯至 `media` 的背景圖，非必填), `featuredTravel` (關聯至單一 `travel-projects` 以作置頂), `announcement` (可選的全站跑馬燈公告)。

## 6\. Git 與分支協作規範

為確保專案程式碼的安全與多端協作的絲滑，團隊與 AI 代理人必須嚴格遵守以下 Git 分支工作流：

-   main 分支：生產環境主分支。此分支受保護，嚴禁直接推送（Push）代碼。只有通過本地驗證且審查通過的Pull Request (PR)才能合併至此分支。一旦合併，Vercel 將自動觸發CI/CD生產環境部署。
    
-   dev 分支：日常開發與整合分支。所有的功能分支在完成本地測試後，必須先合併至 dev 分支進行多端聯調與自動化架構校驗。
    
-   功能分支 (feature/\*)：新功能 (如 feature/blog-module, feature/member-timeline) 必須基於最新版 dev 分支拉取獨立功能分支進行隔離開發。
    
-   修復分支 (bugfix/\* 或 hotfix/\*)：常規錯誤與緊急線上故障修復，須拉取獨立分支並在驗證後快速合併。

## 7\. Payload 核心開發工作流

開發團隊與 AI 代理人必須嚴格執行以下標準化工作流，以維護單一真理源：

1.  啓動本地開發: 執行 pnpm dev, Next.js 與 Payload CMS v3 將同時在本地啓動。
    
2.  修改資料模型：任何欄位的增減或關係變更，必須僅在 collections/ 目錄下的原始碼檔案中進行。
    
3.  生成資料庫遷移：修改完成後，Payload 將自動檢測變更，開發者需手動執行 pnpm payload migrate:create \[migration-name\] 生成具備時間戳記的PostgreSQL 遷移指令碼。
    
4.  應用遷移與驗證：執行 pnpm payload migrate 將變更套用至 Supabase 本地或開發資料庫，並前往 [http://localhost:3000/admin](http://localhost:3000/admin) 驗證後台 UI 與權限限制。

## 9\. 技術邊界與極致效能規範 (Rules for AI)

當AI代理人進行代碼編寫與架構迭代時，必須強制遵循以下工程邊界，違反者將被判定為重大架構缺陷：

! 核心限制與工程邊界 (Strict Technical Bounds)

-   **嚴禁手寫資料庫 Schema**: Payload CMS 採用的 Collection 結構為系統唯一真理源。嚴禁手動編寫或修改 Prisma/Drizzle Schema, 所有資料表更動必須透過修改 Collection 設定並自動生成資料庫遷移 (Migration) 檔案執行。

-   **Schema-First 絕對開發順序（數據模型優先）**：AI 代理人在構建任何前端 UI 視圖前，必須先完成 Payload CMS 的 Collection 模型搭建，並運行 `payload generate:types` 生成全域 TypeScript 類型定義文件（`payload-types.ts`）。前端所有 React 組件的數據消費必須嚴格引入並繼承此類型定義，嚴禁在前端組件中手寫 Any 或鬆散的 Interface 結構，確保前後端數據流絕對契合。

-   **全域圖片資產容錯流與 Fallback UI（圖片資產映射規範）**：
    1. 所有 Collection（如 `TravelProjects`, `Media`）中的圖片/多媒體關聯字段，在現階段必須配置為 `required: false`，確保無圖狀態下系統能正常錄入和運行。
    2. 前端 Next.js 組件在渲染圖片時，必須建立嚴密的條件渲染機制。若 Payload 返回的圖片 URL 為空或未指定，嚴禁渲染破損的 HTML 圖片圖標。
    3. 針對無圖狀態，必須統一渲染符合本項目“現代科技感/毛玻璃（Glassmorphism）”視覺體系的 **Fallback UI 佔位色塊**（例如：淡色漸變微光紋理 + 居中顯示該行程/模塊名稱 + 極簡相機 Icon）。
    4. 最終圖片交由用戶在系統部署後，登錄 `localhost:3000/admin` 後台手動上傳替換，前端自動感知並無縫切換為真實高級配圖。
    
-   **嚴禁在客戶端洩漏密鑰**: PAYLOAD\_SECRET、DATABASE\_URI 以及 R2\_ACCESS\_KEY\_ID 和 R2\_SECRET\_ACCESS\_KEY 必須嚴密保留在 Server 側，絕不允許進入 “use client” 組件。
    
-   **大圖瀑布流優化**: 所有相簿與 Blog 封面必須嚴格配置 Next.js 的 sizes 屬性。對於動態 Canvas 或複雜 3D 卡片組件，強制使用 next/dynamic 的 { ssr: false } 進行非同步載入，確保網站 LCP 評分穩居世界頂級 (95分以上)。
    
-   **去中心化資料備份**: 後台必須實作一鍵導出指令，點擊後可在 10 秒內將 Supabase 內的所有文字、評論、大事記與部落格打包成單一 JSON 包，並提供 R2 備份清單，達成極致的數位遺產安全維護。

-   **首頁並行數據獲取 (Parallel Data Fetching)**：域家庭首頁需要同時聚合 Members, TravelProjects, Posts, 以及 HomeConfig 等多個資料源。前端在 src/app/(app)/page.tsx 中，必須強制使用 Promise.all() 並行觸發對 Payload 本地封裝函式的請求，嚴禁瀑布流式 (Waterfall) 的阻塞請求，以確保首頁的極致加載效能 (TTFB 極小化)。
