## 1\. 专案愿景与世界级审美标准

Web Li 是一个定位为长期运营、承载数十年家庭记忆与情感的数字圣殿。本专案不以「完成基础功能」为终点，而是全面对标世界一流（World-Class）网页设计、产品工艺细节、人机互动、长期可持续性与隐私安全。本文件作为AI代理人（Claude Code / CODEX / Google Antigravity 等）与开发团队的最高指导原则。

### 1.1 氛围感知美学 (Ambient UI)

全站拒绝采用死板、突兀的深色/浅色切换。系统必须实作动态色彩过渡美学（Dynamic Thermography），让网页物理氛围随著当前浏览的主角或内容进行「呼吸式」转变：

-   Tavis Li (爸爸)：当切换至Tavis的页面或半导体科技板块时，全站的滚动条、毛玻璃边框与动态背景将平滑过渡为 Google/Apple 风格的极简冷调科技蓝。
    
-   Lynn Chien (妈妈)：当切换至Lynn的页面时，全站色调转入暖调莫兰迪米黄，营造优雅、温润的高雅视觉。
    
-   Leo Li (儿子)：当切换至Leo的页面时，全站过渡为赛博极客风（深黑底色配上丝滑的萤光绿微弱光晕）。
    

### 1.2 电影级动态与微互动

极致的质感来自于隐显之间的微小细节。所有动画效果必须遵循物理规律，拒绝线性过渡。

-   Canvas 粒子动画：首页与各欢迎区的粒子动画不可仅是随机漂浮，需具备鼠标引力磁场与滚动驱动动画 (Scroll-driven Animations)。
    
-   文字动画：文字在滚动时应具备从毛玻璃后方逐渐聚焦放大的电影质感。
    
-   3D Hover 特效：所有卡片元素均需配置 3D Hover 倾斜特效与弹簧物理动画 (Spring Physics)。

## 2\. 系统技术栈选型 (Tech Stack)

基于长期的效能、托管成本与可维护性评估，全面采用以下现代高扩展架构：

| 核心模组 | 选型技术 | 架构定位 |
| --- | --- | --- |
| 核心网页框架 | Next.js 15 (App Router, TypeScript) | 全栈渲染、Server Components 效能优化。版本需符合 Payload 官方兼容矩阵，优先采用 Next.js 15.4.x（最低 15.4.11）。 |
| 内容管理系统 | Payload CMS v3 (Embedded inside Next.js) | 单一真理源 (Single Source of Truth) |
| 资料库系统 | Supabase PostgreSQL (连接池模式) | 动态数据与持久化存储 |
| 媒体与文件储存 | Cloudflare R2 (S3 Adapter) + Cloudflare CDN | 海量相片与图片高画质存储及分发。<br><br>影像优化管道：Cloudflare Transform (自动转换 WebP/AVIF 格式与尺寸压缩) |
| 多语系支援 | next-intl (预设: zh-TW, 备用: en) | 全站静态与动态内容国际化 |
| 前端样式与动画 | Tailwind CSS / shadcn/ui / Framer Motion | 原子化样式、Radix 原生无障碍组件与物理动画 |
| 部署与 CI/CD | GitHub Repository + Vercel Deployment | 自动化流水线, main 分支推送即时部署 |

### 核心架构约束

1.  **零原生影片储存**：专案严禁提供上传、解码或串流原生影片档案（如 .mp4, .mov）的功能。所有影片在资料模型与 UI 层，均需以「YouTube 外部连结网址」的形式存在。多媒体组件遇到影片类型时，需调用 YouTube Thumbnail API 渲染预览图，并透过前端灯箱（Lightbox）内嵌 iframe 进行播放。
    
2.  **媒体储存去 Vercel 化**：所有相片及静态图片资产，必须透过 S3 适配器上传至 Cloudflare R2。严禁引入 Vercel Blob。
    
3.  **数据库冷启动防护**：数据库已切换至 Supabase PostgreSQL。编写后端与 CMS 连接代码时，必须使用连接池埠（Port 6543）并在连接字串带上 ?pgbouncer=true，以避免 Serverless 连接暴增与冷启动延迟。
    
4.  **数据获取层隔离**：所有数据请求通过src/lib/data/封装函数，前端禁止直接调用Payload Local API

5.  **图片字段容错**: 所有Collection中的图片/媒体关联字段必须设置为required: false

## 3\. 核心功能模组需求

### 3.1 全域家庭大厅 (The Grand Family Lobby / Home Page)

作为 Web Li 数字圣殿的第一接触点，根路由 (/) 必须展现顶级的产品工艺与家庭凝聚力。首页作为全站的数据中枢与流量入口，需具备以下核心特性：

-   **全景英雄首屏 (Hero Section) 与 Ambient UI 零点**：

    -   预设全站基调为高雅极简的「中性毛玻璃 (Neutral Glassmorphism)」。
  
    -   搭配全萤幕的 Canvas 粒子动画。当鼠标悬停或滑动至特定家庭成员的入口卡片时，粒子磁场与全站色调需无缝预加载并过渡至该成员的专属氛围（如：指向 Tavis 时转为科技蓝，指向 Lynn 时转为莫兰迪黄）。

-   **家族成员矩阵入口 (Family Portal)**：

    -   透过 3D Hover 物理弹簧卡片，展示 6 位家庭成员（Tavis, Lynn, Nini, Leo, Sophie, Grandma）的动态立绘或质感头像。

    -   卡片需呈现成员的「一句话动态或当前状态（Status）」，点击后通过丝滑的页面过渡动画进入原定的「个人首页」。

-   **动态聚合看板 (Dynamic Feed Hub)**：

    -   **近期足迹**：自动提取 TravelProjects 中「规划中」与最新「已完成」的行程横幅（Banner），提供快速一键参与评论与点赞的入口。

    -   **家庭速报**：聚合最新的 Premium Family Blog 文章轮播，并展示最新的情感互动留言板摘要。
 
    -   **時空膠囊微縮窗（Time Machine Widget）**：首頁動態拉取歷史上「那年今日（On This Day）」或隨機年份的家庭核心大事記快照與一張歷史相片，作爲跳轉至獨立 3.6 模組 的情感引流入口。
      
    -  **共同願望精簡看板（Bucket List Quick View）**：【家人模式限定】首頁卡片式展示當前「進行中」優先級最高的前 3 項共同願望。支援在首頁直接勾選完成（同步觸發 Canvas 全螢幕煙火特效），並提供「查看完整願望清單」按鈕引導至独立的 3.7 頁面

-   **门禁感知渲染 (Role-Aware Rendering)**：

    -   落实 3.5 的双模隐私机制。未登入的访客仅能看到中性首屏、公开成员入口与公开旅游/文章区块。

    -   家人解锁登入后，首页无感局部刷新，额外浮现「家庭共同愿望清单 (Bucket List)」入口、「年度时光报告预告」以及私密照片瀑布流概览。

每一个旅游项目必须以独立的一个以上网页呈现，其底层数据必须严格解析travel-projects.md及其关联的外部旅游文件。项目区分为「规划中」与「已完成」两种状态。

-   **规划中行程** (如 202607 重庆)：
    
    -   **数据解析源**：严格解析 202607重庆长江三峡8日.md，提取6人出行名单、航班资讯(MU3539, 3U3784)、住宿交通与核心防暑降温提醒。
        
    -   **高密度互动组件**：页面的各项细分内容(如饭店选择、景点排程、费用估算)必须启用让用户添加 comment、Thumb-up 和 Thumb-down 的功能, 人添加评论(comments)、点赞(Thumb-up)与点踩(Thumb-down)的功能，且必须清晰展示操作者的用户名。且必须清晰展示操作者的用户名, 以辅助家庭决策。
        
-   **已完成行程** (如 202308 东澳)：
    
    -   **数据解析源**：严格解析 202308东澳全览9日.md，提取其墨尔本古董蒸汽火车、企鹅归巢、悉尼蓝山等核心里程碑、航班与小费细节。

### 3.4 顶级家庭部落格系统 (Premium Family Blog)

为满足家庭长期的思想沉淀、生活随笔与知识分享需求，全新引入世界级规格的 Blog 模组。

-   **模组化区块编辑器 (Block Editor)**：后台采用 Payload CMS 的 Rich Text (Lexical) 区块系统，支援家人无痛嵌入式多种组件 (如：Markdown 语法、精致的代码高亮区块、流畅的大图排版、YouTube 影片、或是家庭成员专属的投票与代办元件)。
    
-   **深度成员关联**：每篇 Blog 文章需强关联作者（authors），并在前端展示极具质感的作者 Hover Card（浮动卡片），滑动显示该成员的最新动态、精简履历与快速对话通道。并可透过链接跳转到相对应的个人首页。
    
-   **多维度分类与动态标签云**：支援按照多种维度进行交叉筛选。前端实作具备微弱物理碰撞效果的标签云（Tag Cloud）。
    
-   **情感互动留言板**：每篇 Blog 下方除了常规文字评论外，加入专为家人设计的「暖心表情快速回应」（如：温馨、太酷了、赞、辛苦了），且评论与回应必须支持 useOptimistic 乐观更新，达成无延迟互动。
    
-   **多语系SEO优化**：自动生成具备正确语系标签的静态页面(ISR)，内建JSON-LD结构化数据。
    

### 3.5 门禁与双模隐私系统 (Family-Only Secure Gate)

家庭入口网站涉及高度敏感的隐私数据。系统必须具备**公开（Public）与私密（Family-Only）双模切换机制**。

-   **访客模式 (Public)**：未登入的外部访客仅能看见公开的成员介绍、公开 Blog 文章、公开的旅游合影与精简大事记。
    
-   **家人模式 (Private)**：家庭成员通过后台验证或前端安全 Session 暗号解锁后，系统采用无感局部刷新，解锁完整的敏感相册、吐槽点评、详细日程与个人成长足迹。
    

### 3.6 时空胶囊大事记 (Time Machine Timeline)

打破扁平的大事记流水帐，引入「时空滑块（Time Machine Slider）」概念。当使用者在时间轴上拖动年份（例如从2026拖回2013）时，网页主体色调将短暂泛黄，页面透过动态滤镜与动画，自动过渡并聚焦至该年份的家庭核心事件、当时成员的青涩头像与历史相片，创造强烈的情感震撼。

-   **架構定位**：本模組為獨立的前端渲染路由頁面 (/timeline)。打破扁平的大事記流水帳，作為承載家庭數十年長週期記憶的沉浸式空間，並與 3.1 首頁 的微縮窗口進行動態聯動。
  
-   **時空滑塊互動**：引入「時空滑塊（Time Machine Slider）」概念。當使用者在時間軸上拖動年份（例如從2026拖回2013）時，網頁主體色調將短暫泛黃，頁面透過動態濾鏡與動畫，自動過渡並聚焦至該年份的家庭核心事件、當時成員的青澀頭像與歷史相片，創造強烈的情感震撼。

-   **效能隔離防線**：本頁面涉及海量歷史文本與相片載入，數據獲取層（lib/data/timeline）必須實作滾動非同步分頁加載（Infinite Scroll）與圖片 R2 尺寸優化，嚴禁一次性拉取全量數據，確保與首頁物理隔離。

### 3.7 年度时光报告与共同愿望清单 (Wrapped & Bucket List)

本模組由兩個獨立的私密互動路由空間組成，僅在「家人模式（Private）」下全面解鎖，並在 3.1 首頁 保留高互動性的數據輕量化接口。

-   **家庭共同願望看板 (Family Bucket List - 獨立頁面 /bucket-list)**：
  
    - 全家共同維護的看板系統。分為「願望池」、「進行中」、「已實現」三大狀態。
 
    - 當家人在 3.1 首頁微縮組件 或本頁面中勾選完成時，全站即時觸發 Canvas 螢幕煙火特效，並透過 Supabase Webhook 自動將該事件歸檔至 3.5 時空膠囊大事記 中。
    
-   **年度時光報告 (Family Wrapped - 獨立季節性頁面 /wrapped)**：

    -   对标 Spotify Wrapped。每年12月31日系统根据资料库自动产生成员与家庭的年度大数据视觉报告。
 
    -   **首屏聯動**：在發布季期間，3.1 全域家庭大廳 的 Hero Section 將出現極具儀式感的「開啟我們的 2026 年度 Wrapped」全屏彩蛋入口。報告採用全屏 Framer Motion 故事翻頁影音特效，統計過去一年的足跡、照片量、部落格產出與家族互動之最。

### 3.8 終端交互彩蛋 (Leo's Terminal Interaction)

为了展现极客风的极致工艺，Leo Li 页面的黑客终端机组件必须具备真实命令交互能力。家人在输入框内输入help 可顯示隱藏命令列表；輸入 love 觸發全螢幕絲滑流動的綠色二進位代碼雨；輸入 clear 清空終端。以数字化彩蛋凝聚家庭趣味。

## 4\. 目录结构规范 (Directory Structure)

为了最大化多智能体（Multi-Agent）与 AI 辅助开发（Vibe Coding）的效能，本专案采用“强隔离”的目录架构。业务说明档、纯净内容源与前端/后端代码必须严格分立，避免 AI 在扫描全局时产生上下文污染或误操作。

目录结构规范如下：

### 4.1 专案结构要求

专案结构必须保持高度模组化，明确划分「通用组件」与「业务功能域」，以利多代理（Multi-Agent）并行开发时减少代码冲突。其他规范如下：

1.  **统一的源码隔离 (The src Directory)**：所有应用代码必须放置在 src/ 目录下。这使得根目录仅保留环境设定与文档，极大地降低了 AI 代理人在执行终端操作时的路径误判率。
2.  **严格边界**：禁止将带有业务逻辑的组件直接丢进 src/components/。必须采用 Feature-Driven 架构。你所开发的代码若属于特定业务，必须严格限缩在 src/features/[member|timeline|travel|home|admin]/ 资料夹内，以确保与其他并行开发的智能体互不干涉。
3.  **数据调用防护**：前端任何 Server/Client 组件均不得直接调用 Payload 的 Local API（如 payload.find）。所有数据请求必须导向 src/lib/data/ 层对应的封装函式。
4.  **效能与 SEO 要求**：
    -   所有前台 `page.tsx` 必須包含 `generateMetadata` 导出，且必须妥善处理图片的 Open Graph 预览 URL。
    -   所有图片组件必须使用 Next.js `Image` 并配置精确的 `sizes` 属性。
    -   复杂动画组件必须使用 next/dynamic 进行非同步载入。

### 4.2 全域原始数据隔离与内容源数据（content source）规范

为了确保全栈架构的纯净度，并为后续自动化数据灌录（Data Seeding）打下基础，系统强制执行「程式码与原始内容完全解耦」原则：

1. **专属目录设立与结构定义**：于专案根目录下设立独立的 `content-source/` 资料夹（内含 `profiles/` 与 `travels/` 子目录）。严禁将原始 Markdown 内容文件混入 `src/app/` 或 `src/components/` 等程式码核心目录。
3. **单一事实来源（SSOT）**：`content-source/` 内的 Markdown 文件为系统初始化的唯一文本依据。
4. **动态扩充性与自动化构建（核心架构要求）**：未来新增旅游项目或个人档案时，用户只需将新的 `.md` 文件放入 `content-source/travels/` 或 `content-source/profiles/`。系统后续开发的自动化脚本（Seeding Scripts）必须具备遍历该目录、解析 Markdown 内容并动态新增至 Payload 数据库条目的能力。
5. **前端路由动态感知（防呆红线）**：前端页面必须透过动态路由（Dynamic Routing，如 `[slug]` 或 `[id]`）自动读取数据库内容并渲染。**严禁在应用程式中手写硬编码（Hardcoded）的死路由**。
6. **Token 消耗优化**：在开发前端视图时，AI 代理人应直接引用 Payload 自动生成的强类型（`payload-types.ts`），严禁在前端组件中直接引入或重复扫描解析 `content-source/` 内的大型文本文件。

## 5\. 核心资料模型设计 (Payload Collections)

Payload CMS 的 Collection 配置是本系统资料库的唯一真理源 (Single Source of Truth)。本章节仅定义业务层面的数据结构与约束，开发代理 (AI Agent) 必须自行查阅最新 Payload v3 官方文件，使用最新的语法（如 import type { CollectionConfig } from 'payload'）来实现具体的 TypeScript 代码。

### 5.1 Posts (部落格文章模型)

* **定位**：承载家庭的思想沉淀与生活随笔。
* **权限设定 (Access Control)**：已登入的家庭成员可读取所有文章；未登入访客仅能读取 `isPrivate: false` 的公开文章。

| 字段名称 (Name) | 数据类型 (Type) | 必填 (Required) | 业务设定与说明 (Description / Settings) |
| --- | --- | --- | --- |
| title | text | 是 | 支援多语系 (localized: true)。在 Admin UI 作为标题显示。 |
| slug | text | 是 | 唯一值 (unique: true)。 |
| author | relationship | 是 | 关联至 `users` Collection。 |
| categories | relationship | 否 | 关联至 `categories` Collection，支援多选 (hasMany: true)。 |
| isPrivate | checkbox | 否 | 预设为 `true`。标示为私密文章（仅限家庭成员）。 |
| publishedDate | date | 是 | 文章发布日期。 |
| coverImage | relationship | 否 | 关联至 `media` Collection。（注：Phase 1 设为非必填以容错） |
| content | richText | 是 | 必须使用 Lexical 区块编辑器，支援多语系。 |
| tags | array | 否 | 包含子字段 `tag` (text)。 |

### 5.2 TravelProjects (旅游行程模型)

* **定位**：管理「规划中」与「已完成」的家族旅游专案，并与外部 Markdown 档案建立对应。

| 字段名称 (Name) | 数据类型 (Type) | 必填 (Required) | 业务设定与说明 (Description / Settings) |
| --- | --- | --- | --- |
| title | text | 是 | 支援多语系。在 Admin UI 作为标题显示。 |
| status | select | 是 | 选项：`['planning', 'completed']`。 |
| isPrivate | checkbox | 否 | 预设为 `true`。 |
| startDate | date | 是 | 行程开始日期。 |
| endDate | date | 是 | 行程结束日期。 |
| externalDocIdentifier | text | 否 | 对应 `content-source/travels/` 下外部 Markdown 文件的识别码。 |
| coverImage | relationship → media | 否 | 封面照片、图片。 |
| members | relationship → users (hasMany) | 否 | 参与成员。 |

### 5.3 Comments (全站情感互动模型)

* **定位**：统一管理全站（文章、旅游规划、大事记）的留言与表情互动。

| 字段名称 (Name) | 数据类型 (Type) | 必填 (Required) | 业务设定与说明 (Description / Settings) |
| --- | --- | --- | --- |
| user | relationship | 是 | 关联至 `users` Collection。 |
| associatedType | select | 是 | 选项：`['travel', 'timeline', 'blog']`，标明此留言属于哪个模组。 |
| associatedId | text | 是 | 关联模组的具体内容 ID（例如某篇文章的 ID 或某个行程的 ID）。 |
| commentText | textarea | 否 | 用户的文字留言（若仅发送表情则为空）。 |
| reaction | select | 否 | 选项：`['none', 'up', 'down', 'heart', 'cool', 'applause']`。 |
| createdAt | date | 是 | 留言建立的时间戳记。 |

### 5.4 Media (媒体流水线模型)

配合 Cloudflare R2，所有相片上传流程由 afterChange 钩子 (Hook) 自动触发 Sharp 处理。原始高画质图留存 R2，前端根据 sizes 栏位异步加载 400px (Thumbnail), 800px (Medium), 1600px (Large) 的 WebP 图片，严格杜绝 LCP 效能瓶颈。

* **开发特别注意**：在 Phase 1 本地开发阶段，**请先配置为本地存储（允许写入本地资料夹）**，以确保系统可顺利启动与验证。后续 Phase 才会引入 Cloudflare R2 S3 Adapter，严禁在初始阶段加入 `disableLocalStorage: true`。

| 字段名称 (Name) | 数据类型 (Type) | 必填 (Required) | 业务设定与说明 (Description / Settings) |
| --- | --- | --- | --- |
| type | select | 是 | 选项：`['photo', 'video']`。预设为 `photo`。 |
| youtubeUrl | text | 否 | 仅当 `type` 为 `video` 时显示于后台。需加入 Regex 验证确保为合法 YouTube 网址。 |
| altText | text | 是 | 支援多语系。用于无障碍说明与 SEO。 |
| tags | array | 否 | 包含子字段 `tag` (text)。 |
| relatedMembers | relationship | 否 | 关联至特定的家庭成员 (hasMany: true)。 |
| relatedTravel | relationship | 否 | 关联至特定的旅游行程 (hasMany: false)。 |

* **图片处理要求**：后台需配置 `imageSizes`，自动裁切并产生 `thumbnail` (400px), `medium` (800px), `large` (1600px) 三种尺寸。

### 5.5 SiteConfig (全站設定 - Global)

* **定位**：为了保持单一真理源，全站唯一的设定资讯必须配置在 Payload 的 `Globals` 中，而非 `Collections`。

**A. SiteConfig (系统底层设定)**

* 字段包含：`siteName` (多语系文字), `siteDescription` (多语系文本区), `contactPhone`, `contactEmail`, `contactAddress` (多语系)。
* 阵列字段：`socialLinks`，包含 `platform` (下拉选单如 github, linkedin) 与 `url`。

**B. HomeConfig (首页动态配置)**

* 权限设定：必须设定为公开可读 (`read: () => true`)。
* 字段包含：`heroTitle` (预设 'Welcome to Web Li'), `heroSubtitle`, `heroBackground` (关联至 `media` 的背景图，非必填), `featuredTravel` (关联至单一 `travel-projects` 以作置顶), `announcement` (可选的全站跑马灯公告)。

## 6\. Git 与分支协作规范

为确保专案程式码的安全与多端协作的丝滑，团队与 AI 代理人必须严格遵守以下 Git 分支工作流：

-   main 分支：生产环境主分支。此分支受保护，严禁直接推送（Push）代码。只有通过本地验证且审查通过的Pull Request (PR)才能合并至此分支。一旦合并，Vercel 将自动触发CI/CD生产环境部署。
    
-   dev 分支：日常开发与整合分支。所有的功能分支在完成本地测试后，必须先合并至 dev 分支进行多端联调与自动化架构校验。
    
-   功能分支 (feature/\*)：新功能 (如 feature/blog-module, feature/member-timeline) 必须基于最新版 dev 分支拉取独立功能分支进行隔离开发。
    
-   修复分支 (bugfix/\* 或 hotfix/\*)：常规错误与紧急线上故障修复，须拉取独立分支并在验证后快速合并。

## 7\. Payload 核心开发工作流

开发团队与 AI 代理人必须严格执行以下标准化工作流，以维护单一真理源：

1.  启动本地开发: 执行 pnpm dev, Next.js 与 Payload CMS v3 将同时在本地启动。
    
2.  修改资料模型：任何栏位的增减或关系变更，必须仅在 collections/ 目录下的原始码档案中进行。
    
3.  生成资料库迁移：修改完成后，Payload 将自动检测变更，开发者需手动执行 pnpm payload migrate:create \[migration-name\] 生成具备时间戳记的PostgreSQL 迁移指令码。
    
4.  应用迁移与验证：执行 pnpm payload migrate 将变更套用至 Supabase 本地或开发资料库，并前往 [http://localhost:3000/admin](http://localhost:3000/admin) 验证后台 UI 与权限限制。

## 9\. 技术边界与极致效能规范 (Rules for AI)

当AI代理人进行代码编写与架构迭代时，必须强制遵循以下工程边界，违反者将被判定为重大架构缺陷：

! 核心限制与工程边界 (Strict Technical Bounds)

-   **严禁手写资料库 Schema**: Payload CMS 采用的 Collection 结构为系统唯一真理源。严禁手动编写或修改 Prisma/Drizzle Schema, 所有资料表更动必须透过修改 Collection 设定并自动生成资料库迁移 (Migration) 档案执行。

-   **Schema-First 绝对开发顺序（数据模型优先）**：AI 代理人在构建任何前端 UI 视图前，必须先完成 Payload CMS 的 Collection 模型搭建，并运行 `payload generate:types` 生成全域 TypeScript 类型定义文件（`payload-types.ts`）。前端所有 React 组件的数据消费必须严格引入并继承此类型定义，严禁在前端组件中手写 Any 或松散的 Interface 结构，确保前后端数据流绝对契合。

-   **全域图片资产容错流与 Fallback UI（图片资产映射规范）**：
    1. 所有 Collection（如 `TravelProjects`, `Media`）中的图片/多媒体关联字段，在现阶段必须配置为 `required: false`，确保无图状态下系统能正常录入和运行。
    2. 前端 Next.js 组件在渲染图片时，必须建立严密的条件渲染机制。若 Payload 返回的图片 URL 为空或未指定，严禁渲染破损的 HTML 图片图标。
    3. 针对无图状态，必须统一渲染符合本项目“现代科技感/毛玻璃（Glassmorphism）”视觉体系的 **Fallback UI 占位色块**（例如：淡色渐变微光纹理 + 居中显示该行程/模块名称 + 极简相机 Icon）。
    4. 最终图片交由用户在系统部署后，登录 `localhost:3000/admin` 后台手动上传替换，前端自动感知并无缝切换为真实高级配图。
    
-   **严禁在客户端泄漏密钥**: PAYLOAD\_SECRET、DATABASE\_URI 以及 R2\_ACCESS\_KEY\_ID 和 R2\_SECRET\_ACCESS\_KEY 必须严密保留在 Server 侧，绝不允许进入 “use client” 组件。
    
-   **大图瀑布流优化**: 所有相簿与 Blog 封面必须严格配置 Next.js 的 sizes 属性。对于动态 Canvas 或复杂 3D 卡片组件，强制使用 next/dynamic 的 { ssr: false } 进行非同步载入，确保网站 LCP 评分稳居世界顶级 (95分以上)。
    
-   **去中心化资料备份**: 后台必须实作一键导出指令，点击后可在 10 秒内将 Supabase 内的所有文字、评论、大事记与部落格打包成单一 JSON 包，并提供 R2 备份清单，达成极致的数位遗产安全维护。

-   **首页并行数据获取 (Parallel Data Fetching)**：域家庭首页需要同时聚合 Members, TravelProjects, Posts, 以及 HomeConfig 等多个资料源。前端在 src/app/(app)/page.tsx 中，必须强制使用 Promise.all() 并行触发对 Payload 本地封装函式的请求，严禁瀑布流式 (Waterfall) 的阻塞请求，以确保首页的极致加载效能 (TTFB 极小化)。
